Review a Change

Ask for the user-visible outcome, then let Lindy expose the relevant declarations. Keep inspection, proposal, human review and mutation as separate steps.

Inspect before proposing

For the starter task, inspect view.EditReadingItem and operation.RemoveReadingItem. The view has a save action; the remove operation and datasource capability already exist. Check the existing list view so the agent can explain what stays unchanged.

Review the semantic diff

A proposal is read-only. Review its normalized patch, changed and affected IDs and diagnostics. Applicable means the candidate passed the relevant checks; it does not grant human approval.

Approve one revision

Approve the exact proposal. The graph patch carries the full revision returned by that proposal as expectedRevision. If the graph changed, inspect and propose again rather than silently substituting a new revision. Client permission to dispatch a tool is separate from approval of the application change.

Validate, compile and inspect the result

After applying, validate the new graph, compile that returned revision and restart the same preview. If mutation output is lost, inspect before retrying; interruption does not establish rollback.

Review content changes too

This documentation site has a separate typed-record maintenance workflow in One Reviewed Change. It is a case study, not the portable starter.

Example: Remove item

text
Add a confirmed Remove item action to the editor.
Preserve the existing list and edit flow.
Inspect the semantic graph, propose the change, and wait for my approval.

Illustrative agent reply, not a recorded model response: “I found the editor and the existing remove operation. I’ll propose one confirmed action on view.EditReadingItem. The list, Save changes and data interfaces stay unchanged. I haven’t applied it; please review the proposal.”

Selected actual proposal fields (revision and patch omitted; node references retain only IDs):

json
{
  "ok": true,
  "result": {
    "applicable": true,
    "changed": [
      {
        "id": "view.EditReadingItem"
      }
    ],
    "affected": [
      {
        "id": "application.ReadingList"
      },
      {
        "id": "view.EditReadingItem"
      }
    ]
  }
}

A separate affected call with that changed ID returns application.ReadingList and view.EditReadingItem in result.semantic. The application depends on the view; being affected does not mean its declaration was edited. Source bytes remain unchanged at proposal time.

Example human approval: “Approve this Remove item action only; preserve the list and edit flow.” The agent applies the same patch using the full proposal revision. Successful output has applied: true; previousRevision matches the reviewed value. The graph workflow does not use the documentation-content approvalHash.
