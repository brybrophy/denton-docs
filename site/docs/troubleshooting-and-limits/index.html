Find the symptom below before retrying a command. Keep the candidate checksum/version, Node/npm version and the specific diagnostic when requesting help. Never share credentials, a private preview URL, cookies or project content you cannot disclose.

Candidate installation fails

Use Node.js 24.19.0 and the supplied local lindy-candidate.tgz. Install into the new .lindy-tools prefix with npm offline and scripts disabled. No registry command is live yet. Check the file/checksum rather than searching for a similarly named npm package. Source contributors keep their separate setup guide.

Lindy command is not found

Use the local executable from the directory where you installed the archive: ./.lindy-tools/node_modules/.bin/lindy. A global lindy command is not installed. For preview, reading-list/START-HERE.txt contains an absolute command pointing to the installed CLI and reading-list/lindy.graph.json. Moving either folder breaks that saved path; reconnect deliberately rather than substituting another executable.

The agent cannot see the tools

First enter reading-list, where mcp.json, permissions.json and .codex/config.toml were generated. Inspect those files, start your existing client from that directory and check /mcp for one server with eight Lindy tools. Preserve permission prompts. The sample does not install a model, sign in or choose a provider; a real client session and an outside guide-only run remain separate checks.

A proposal or artifact is stale

Compare the current graph revision with the expectedRevision in the failed request. If they differ, inspect what changed before preparing another proposal. Artifact reads also need the manifest hash for the selected current build. Do not merely replace the hash in an old approved patch or reapply an action that is already present.

The preview shows the old page

Check that the command points to reading-list/lindy.graph.json for the sample you edited. Stop its old preview, restart the saved command and open the new private one-use URL; an old tab may still refer to the previous session. Open an item’s editor—not just the list—to find Remove item. If the port is busy, stop the other preview or choose --port 4174 explicitly. Lindy does not pick another port or kill a process for you.

Sample data disappears

The preview uses session memory. Each start seeds the sample records again, so edited or removed item data does not survive a restart. The semantic graph is a different file: the approved Remove item action stays in reading-list/lindy.graph.json and appears again in the rebuilt editor.

Content validation fails

This full documentation website is a different application with typed content. Its maintainers use docs:author and source-specific checks. The portable starter edits a reading-list graph; do not copy the docs-site content workflow into it.

A preview will not start

The candidate contains its runtime; do not install packages into generated files to repair it. Check supported Node, artifact checksum, project validation and exact port. If the graph or archive is damaged, preserve it for diagnosis and use a fresh candidate/project rather than overwriting an existing graph.

Know the supported boundary

The first preview contains one local reading-list starter. Production storage/connectors, a starter picker, Homebrew and an official pack gallery are deferred. Deterministic MCP/HTTP tests are not a claim that a live agent conversation or every client/platform has been verified.

Example: Remove item

In this failure, the Remove item patch succeeded, but the next compile request still used the pre-edit graph revision. The compiler refuses to build under that stale identity. These are selected actual failure fields:

json
{
  "status": "project-failure",
  "diagnostics": [
    {
      "code": "E601",
      "kind": "project-compilation-revision-conflict",
      "message": "The project revision has changed.",
      "repairClass": "reload-and-recompile"
    }
  ]
}

Inspect view.EditReadingItem in the current graph. Confirm the approved remove action is present and the save/list relationships are unchanged; compare the current graph revision with the successful patch’s returned revision. Compile that approved state with the same sample configuration. The successful response includes:

json
{
  "status": "success"
}

Do not add the same remove action again. If the graph contains unrelated changes, stop for a new proposal and review. If compilation succeeds but the old editor remains on screen, restart preview and open its new private link. The action then appears, while the two sample records are reseeded.
