Convention Packs

Author a Team Pack

On this page

On this page

  • Declare the rules
  • Verify the host and compare output
  • Test a local manifest

Your design system and engineering standards can travel with your applications. A team pack gives Denton a versioned description of the choices you want products to share, from brand typography and component libraries to database naming. Start with one recurring decision. Pick a supported recipe, the compiler implementation that generates that part of the application, and configure its rules in a team-owned manifest.

Declare the rules

For a design-system pack, give the manifest a team-owned ID and version. Set colors by role, define body and heading font stacks, and choose cell spacing and empty-state text. To use a shared component library, map the table and button roles to named exports from an exact package version.

Here is the components portion of an illustrative team manifest. It tells Denton which imports to generate. The team supplies the library and a complete presentation manifest.

json
{
  "components": {
    "package": "@acme/design-system",
    "version": "1.0.0",
    "tableExport": "DataTable",
    "buttonExport": "ActionButton"
  }
}

The table adapter must pass children through to a semantic table. The button adapter must pass the ref, event handlers and attributes through to a native button. Those details let a keyboard user cancel a destructive action and recover focus regardless of which design system supplies the button.

Verify the host and compare output

Install the trusted component library in the application that will render the generated code. From the root of a Denton source checkout with dependencies installed, check that the host resolves the exact library version in your manifest. Replace both example paths with your own.

sh
node scripts/convention-packs.mjs verify-host /path/to/team-pack.json /path/to/host

Propose the same application requirements twice, once with the built-in pack and once with the team manifest. Review the selected components, styles, dependencies and generated file hashes. Confirm that the application still exposes the same operations and arguments. Share the reviewed manifest and its version with the projects that should adopt it.

Test a local manifest

Exercise a representative view or operation twice: once with the built-in pack and once with your team manifest. Check the intended differences and verify that the application behavior still matches the approved proposal.
