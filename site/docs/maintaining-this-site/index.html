One Reviewed Change

On this page

On this page

  • Inspect the source
  • Review one proposal
  • Apply the exact approved edit
  • Rebuild and observe

Try a small content change to this site: update the Overview introduction while preserving its links, page identity and navigation. Your agent should inspect the typed record, propose the exact edit and wait for review.

Inspect the source

Ask your agent to inspect Overview in apps/lindy-docs/site.content.json. Its opening block is one plain paragraph with no inline links. The rest of the page contains links that this edit must preserve. Routes and shared behavior stay in lindy.graph.json.

text
Update the Overview introduction to explain our application more clearly.
Inspect its typed content first and propose one scoped edit.
Preserve the page ID, URL, navigation and existing links.
Show me the semantic diff and wait for approval before applying it.

Illustrative agent reply: “I found one plain paragraph in Overview at block 0. I’ll propose a clearer semantic blueprint introduction. I’ll preserve the page ID, URL, navigation and every existing link elsewhere on the page. I haven’t applied anything; I’m waiting for your review.”

The reply is illustrative, not a recorded model conversation. Tool excerpts below show the deterministic results for this example; omitted fields are noted. An agent may suggest different wording.

sh
pnpm docs:author inspect --page overview

Selected raw inspect fields (the document and current revision are omitted here):

json
{
  "model": "docs.ContentPage",
  "pages": [
    {
      "id": "overview",
      "slug": "overview",
      "title": "Overview",
      "section": "Start Here"
    }
  ]
}

Review one proposal

Before — Lindy gives your coding agent an explicit model of what an application does. The agent can inspect behavior and relationships, propose one scoped change, and compile the approved result instead of rebuilding its understanding from implementation files.

After — Lindy gives your coding agent a semantic blueprint of an application: its data, actions and views. The agent can inspect that model, propose one scoped change for your review, then deterministically compile the approved source into application artifacts.

The agent writes overview-change.json with the full current expectedRevision returned by inspect and the following operations. This is a request excerpt, not a Lindy response; the text value is the After paragraph above.

json
{
  "operations": [
    {
      "kind": "set-block-text",
      "pageId": "overview",
      "blockIndex": 0,
      "text": "Lindy gives your coding agent a semantic blueprint of an application: its data, actions and views. The agent can inspect that model, propose one scoped change for your review, then deterministically compile the approved source into application artifacts."
    }
  ]
}

set-block-text is appropriate here because block 0 is plain. For a paragraph containing links or marks, use replace-block and preserve its inline structure. This proposal changes only docs.ContentPage/overview, block 0; page identity, URL, order, other blocks and links stay unchanged.

sh
pnpm docs:author propose \
  --request overview-change.json

Selected raw proposal fields (full before/after records and revision hashes omitted):

json
{
  "valid": true,
  "changes": [
    {
      "semanticId": "docs.ContentPage/overview",
      "beforeOrder": 0,
      "afterOrder": 0
    }
  ]
}

Read-only proposal status: valid, not applied. The source bytes are still unchanged. Review the Before/After text and the unchanged page relationships before approving. The real response also supplies candidateRevision and proposalHash; keep the full proposalHash, not an abbreviated display value.

Apply the exact approved edit

Example human approval: “Approve exactly this Overview paragraph change. Apply the reviewed request with its full proposal hash.” This message is human approval, not a tool result or automatic permission.

The agent sets proposalHash to the complete value returned by that proposal and sends the same overview-change.json. Do not shorten the hash, change the request or substitute a new revision after review.

sh
pnpm docs:author apply \
  --request overview-change.json \
  --approve "$proposalHash"

Selected raw apply field:

json
{
  "applied": true
}

The returned revision equals the earlier candidateRevision; previousRevision equals the inspected revision. A changed source makes the old request fail with Documentation authoring: stale-revision. Inspect and propose again; do not silently refresh an approved request. If publication is uncertain, inspect before any retry.

sh
pnpm docs:author validate

Selected raw validation fields (the new revision is omitted):

json
{
  "valid": true,
  "pages": 11
}

Rebuild and observe

sh
pnpm docs:preview

After the approved edit, open /docs/overview. Its first paragraph now reads:

Lindy gives your coding agent a semantic blueprint of an application: its data, actions and views. The agent can inspect that model, propose one scoped change for your review, then deterministically compile the approved source into application artifacts.

Search blueprint in the site search box. Overview is now one of the results; open it to read the new paragraph. This walkthrough may also match because it quotes the example.

This tutorial itself does not replace the real Overview introduction. Your agent applies an edit only after your review. No generated HTML, projected Markdown or runtime file is a maintenance input.

The same API can add a page with its title, slug, section and position in one reviewed candidate. Include inbound link changes in that request when needed. Changes to graph behavior use the separate Review a Change workflow; Artifacts explains build identity.
